# Capability and activation design

The owner authorized the complete initiative after challenging a small-pilot
recommendation. Capability implementation therefore covers both native frameworks
and the full design chain. Measurement remains evidence-bound.

## Contracts and review — TASK-18

Create explicit surface contracts with a task reference, job, mode, change scope,
existing product/design authority, targets, material states and criterion IDs.
Context loading reports hashes, omissions and character limits; it never invents
token savings or hides omitted authority. Planned targets are allowed for context;
review requires materialized files. Separate initial judgment, subsequent detector
evidence and verification. Reject stale or edited receipts and mismatched artifacts.

## Detector and native feedback — TASK-19

Install only an explicitly chosen, SHA256-pinned machine executable. Never accept
an executable path from a project contract or download through a hook. Local scans
are bounded by time and output; preserve raw results and operational failures.
Include linked local stylesheet hashes. Optional project feedback is independent
per runtime, additive to native hook manifests, deduplicated by session/content/pin
and reversible without removing unrelated hooks.

## Specialists and visual iteration — TASK-20

Strengthen sd/uxd/uids/uid/ta/me/qa in both authoritative source trees. Preserve
walkthroughs, design authority and native orchestration. Provide all focused
actions, actual-capture comparison and external live-tool ownership/recovery.
Do not create another agent hierarchy, review daemon or memory/task store.

## Verification and local activation — TASK-21

Exercise success and failure contracts in isolated temporary projects; run relevant
unchanged regression checks; inspect packaging, CLI/API parity, pins and source
preservation. Verify native manifest commands with representative event replay.
Registration/replay is not proof that an already-running harness reloaded hooks.
Fresh native sessions must demonstrate dispatch before that claim is made.

## Real-work evaluation — TASK-22

Use an existing Control Tower UX walkthrough as a read-only first trial, preserving
the shipping native application. Review before detection, render actual states and
record the findings. A comparison candidate may be created in the isolated trial
workspace; it does not silently change the product or claim owner acceptance.
Longer-term effectiveness requires additional real work and owner decisions.

## Exit evidence

Each implementation task receives a code/documentation WP and QA test WP with
criterion, expected result, observation, tested identity, baseline and artifact.
Only a supported passing verdict and the existing task QA gate permit closure.
Unresolved rollout or empirical claims remain explicit follow-up work in `tc`.
