# Claude Copilot to Codex Copilot Gap Analysis and Parity Plan

Date: 2026-06-09
Claude Copilot source: /Volumes/Dev/Sites/COPILOT/claude-copilot
Codex Copilot target: /Volumes/Dev/Sites/COPILOT/codex-copilot

## Executive Summary

Claude Copilot is currently a mature Claude Code framework at framework version 5.7.0, with componentized `cc` 1.3.0 and `tc` 1.1.0 tooling, 16 specialist agents, command workflows, process-enforcing hooks, task/work-product orchestration, memory, skills, config, known references, Live Docs, worktree/stream orchestration guidance, update/setup workflows, and broad documentation/tests.

Codex Copilot is a focused Codex-native port at 0.3.0. It already has the core native translation: `AGENTS.md`, Codex plugin packaging, direct specialist skills, command-equivalent skills, a `tc` discipline, a `cc` bridge, project setup symlinking, decision-instrument scaffolding, dormant capability packs, and an honest `spawn_agent` boundary. The main gap is not the high-level protocol. The main gap is the surrounding operating substrate that makes Claude Copilot repeatable, inspectable, stateful, and difficult to accidentally bypass.

The parity target should not fake Claude-specific syntax. It should mirror functionality by implementing Codex-native equivalents, and explicitly mark any irreducible runtime boundary.

## Parity Principles

1. Codex-native fidelity over syntax copying. Use skills, AGENTS, plugin metadata, scripts, `tc`, `cc`, and explicit `spawn_agent` workflows.
2. Do not pretend hooks exist. Where Claude uses lifecycle hooks, Codex should provide visible preflight/checkpoint mechanisms plus tests and state records.
3. Keep `tc` the system of record for substantial work, including specs, architecture, test plans, handoffs, and orchestration state.
4. Treat `cc` as shared infrastructure. Codex must either vendor/sync the source or enforce a known-compatible installed version.
5. Import the substance of Claude specialists: success criteria, iteration loops, methodology, routing, QA verdicts, and output compaction.
6. Make parity testable with a machine-readable parity manifest and regression tests.

## Recommended Implementation Plan

### Phase 1: Baseline Parity Manifest and Governance

Create a `parity/` or `docs/parity.md` source of truth recording the Claude baseline inspected here: Claude framework 5.7.0, `cc` 1.3.0, `tc` 1.1.0, 16-agent roster, command roster, hook roster, and feature docs. Add tests that compare Codex's declared surfaces against that manifest. Update `VERSION.json` to include component versions and source baseline, not only Codex package version.

Deliverables:
- `parity/claude-baseline.json` or equivalent
- updated `VERSION.json` component metadata
- tests for agent/skill roster, command-equivalent roster, docs, plugin metadata, setup outputs, and known unsupported Claude runtime surfaces
- docs explaining baseline update process

### Phase 2: Tooling Substrate: `cc`, `tc`, Install, and Version Checks

Choose a dependency model:
- Preferred for true mirror: vendor or submodule `tools/cc` and `tools/tc` from Claude Copilot with sync scripts and version checks.
- Acceptable lighter model: keep external dependency but add setup/update commands that install/check exact compatible versions and fail clearly when missing.

Add Live Docs as an immediate shared behavior. `$ta` and `$me` must call `cc docs get <pkg>` before planning or implementing against installed third-party APIs. `$qa` should use docs when verifying API-sensitive behavior. Add code-execution-path guidance for `tc.api` and `cc.api` when doing multiple related operations.

Deliverables:
- setup/update verification for `cc --version`, `tc version`, `cc config doctor`, and `cc docs sources`
- `$setup-copilot`, `$setup-project`, `$update-copilot`, `$update-project` workflows updated for `cc docs`
- shared behavior and specialist updates for Live Docs and API facade use
- tests using a fixture or mocked command output

### Phase 3: Specialist Roster and Playbook Depth

Mirror the Claude 16-agent roster in Codex-native form. Keep software specialists globally active. Add `kc` as a setup/knowledge specialist. Decide whether `cco`, `cw`, `cs`, and `cpa` become globally available skills or an activated business/creative pack; if the goal is strict mirror, expose them as first-class plugin skills while allowing project policy to ignore them.

Expand each specialist skill using the latest Claude agent substance:

Deliverables:

### Phase 5: Hook Substitute and Quality Gate Mechanics

Codex cannot currently reproduce Claude Code lifecycle hooks from this repo. Implement the strongest native substitute:

- `$me` must store implementation WP and route to `$qa`
- `$qa` must return a verdict and store test WP
- optional script `scripts/copilot-gate.sh` to inspect `tc` for implementation tasks missing QA WPs
- optional `tc` metadata convention: `requiresQa`, `qaStatus`, `qaWpId`, `verifiedAt`
- tests that fail if docs or skills describe QA as optional

Deliverables:
- QA gate state convention in docs and skills
- gate inspection script
- updated `$qa`, `$me`, `$continue`, `$pause`, `$reflect`
- parity docs explaining Claude hook mapping and Codex limits

## Risks and Tradeoffs

- Hook parity is not fully possible without Codex lifecycle hooks. The plan should call this a platform boundary and implement explicit substitutes instead.
- Vendoring `cc`/`tc` gives stronger parity but creates sync maintenance. External dependency checks reduce repository size but keep functionality outside this project's control.
- Adding all 16 specialists globally improves mirror fidelity but may make Codex sessions noisier. A policy-configurable activation model could balance fidelity and focus.
- Expanding skills increases token footprint. Use references and concise local skill bodies where possible, but do not omit operational contracts that materially change behavior.
- Orchestration with `spawn_agent` must remain user-approved under current repo rules. Build launch templates and worktree state first; do not auto-delegate silently.

## Acceptance Criteria for Parity Release

- Codex Copilot declares the Claude baseline it mirrors and has tests for every declared capability.
- A new project setup can install/check `cc`, `tc`, plugin skills, memory/config directories, decision instruments, and task DB without destructive replacement.
- `$protocol` routes bug, technical, experience, physical-digital, UI polish, security, and infrastructure work through the correct specialists.
- `$ta`/`$me` use Live Docs before third-party API work.
- Every specialist has success criteria, workflow, iteration/verification expectations, routing, and compact output contracts.
- QA is structurally required after implementation through skill rules, task metadata, and inspection tests.
- Orchestration supports stream planning, dependency validation, file conflict checks, worktree lifecycle, status, and approved Codex subagent launch instructions.
- Knowledge/extensions/packs have a documented and tested activation path.
- Docs explain implemented/substituted/limited features honestly.
- Version, manifest, setup, docs, and parity tests pass.
