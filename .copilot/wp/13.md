# Claude 5.10.0 Adoption Analysis For Codex Copilot

Date: 2026-06-18
Task: TASK-18
Compared projects:
- Codex Copilot: /Volumes/Dev/Sites/COPILOT/codex-copilot
- Claude Copilot: /Volumes/Dev/Sites/COPILOT/claude-copilot

## Executive Summary

Claude Copilot's important June 17, 2026 update is framework 5.10.0, commit d3e33123d46588f514f98cb78dde952878a06da1: "verification & observability initiative (PRD-7)." The Dependabot commits from the same day are maintenance noise for this strategy question.

The Claude update adds four strategic capabilities:
1. Artifact-gated QA/security verdicts.
2. Declarative agent manifest with routing edges and design chain.
3. Structured validation result contract for failable checks.
4. cc observability additions: memory drift detection and Claude quota usage.

Codex Copilot should adopt the first three strongly, adapt memory drift checks, and treat usage/quota observability as low priority because it is Claude-session-specific and Codex has no matching session-start hook.

Codex Copilot is already ahead on design-led routing in several ways: SOUL.md and architecture-principles decision instruments, an explicit uid stage in the experience chain, product-language ownership in uxd/uids, design-fidelity QA language, and optional packs rather than always-on non-software roles.

The best improvement path is not to import Claude hooks. It is to make Codex's explicit tc/script model more evidence-bound and more declarative.

## Current Codex Strengths

- Protocol routes experience work through sd -> uxd -> uids -> uid -> ta -> me -> qa.
- setup-project scaffolds SOUL.md and architecture guiding principles by default.
- QA already includes design intent, workflow quality, visual fidelity, responsive behavior, accessibility, and product language.
- Optional business/creative specialists are dormant packs, which preserves focus for software projects.
- Codex is honest about runtime limits: no hidden Claude hook enforcement and no autonomous background worker loop.

## Gaps Exposed By Claude 5.10.0

1. QA verdicts are not evidence-bound.
   - Current scripts/copilot-gate.sh accepts VERDICT: APPROVED in a test work product.
   - Claude now rejects bare approval unless an ARTIFACT marker cites a test run, file check, or diff check.
   - For design-led work, Codex should extend this to include design-fidelity evidence.

2. agent-catalog.json is useful but under-specified.
   - Claude manifest has schemaVersion, agents, routingEdges, designChain, role, model, tools, methodology.
   - Codex agent-catalog has agents, optionalAgents, workflows, but no schema, no routing-edge model, and no testable designChain field.
   - This can drift from docs and skills.

3. Validation outputs are inconsistent across scripts.
   - Claude added validation_result.py to standardize pass/fail/warn checks.
   - Codex scripts such as copilot-gate.sh and orchestrate-validate.py currently print custom results.
   - A shared validation result shape would make smoke tests, release fitness, pack validation, and QA gate inspection easier to consume.

4. Memory drift detection is available in cc but not integrated into Codex practice.
   - Installed cc exposes `cc memory check`, though `cc --version` still reports 1.3.0 while Claude VERSION.json says cc 1.4.0.
   - Codex docs/templates mention cc memory search but not drift checks.
   - Since design-led decisions depend on durable memory, drift checks are high leverage.

5. Baseline metadata is stale.
   - Codex VERSION.json and parity/claude-baseline.json mirror Claude framework 5.7.0 and cc 1.3.0.
   - Claude is now framework 5.10.0 and cc 1.4.0.

6. Capability pack metadata has a local consistency gap.
   - docs/packs.md lists writing-legal as an included pack.
   - packs/writing-legal has skills but no pack.json, so activate-pack.py cannot activate it.
   - This is not from Claude 5.10.0, but it weakens the optional-pack model that supports design-led software ecosystems.

## Recommendations

### P0: Update the parity baseline and version contract

Update VERSION.json and parity/claude-baseline.json to acknowledge Claude framework 5.10.0 and cc 1.4.0. Keep the Codex version separate. Add a short note that 5.10.0 is adopted by intent, not by Claude-hook implementation.

Verification:
- scripts/check-versions.sh passes.
- tests/test_mirror_parity.py reflects the new baseline.

### P0: Add artifact-bound QA to the Codex-native QA gate

Update:
- plugins/codex-copilot/skills/qa/SKILL.md
- docs/quality-gates.md
- scripts/copilot-gate.sh
- templates/AGENTS.project.template.md
- tests/test_mirror_parity.py or a new QA gate test file

Codex approval should require:
- Task: TASK-N | WP: WP-N
- ARTIFACT: <type>|<detail>
- VERDICT: APPROVED or VERDICT: APPROVED-WITH-MINOR-FIXES

Recommended artifact types:
- test-run: command, exit code, useful excerpt
- file-check: path and verified property
- diff-check: expected vs actual comparison
- screenshot-check: Playwright or image snapshot evidence for UI work
- a11y-check: accessibility scan or keyboard/focus verification
- design-fidelity-check: explicit comparison against SOUL/spec/work product for product-facing changes

Implementation note: keep this explicit and inspectable through tc. Do not attempt Claude-style runtime blocking.

### P1: Evolve agent-catalog.json into a schema-backed manifest

Either rename agent-catalog.json to agent-manifest.json or preserve the filename and add manifest semantics.

Add:
- schemaVersion
- generatedAt or updatedAt
- agents with role, skill, codex delegation role, purpose, and optional methodology
- optionalAgents with pack and activation info
- routingEdges
- designChain
- schema file

Use it as the source for:
- docs/native-agents.md
- docs/protocol.md workflow checks
- launcher references
- check-versions/smoke tests
- pack validation

This is especially valuable for design-led software because the design chain becomes a testable product contract, not just prose.

### P1: Add shared validation result shape

Create a small Python module, probably scripts/lib/validation_result.py, with CheckResult and ValidationReport semantics matching Claude's pass/warn/fail shape.

Use it from:
- scripts/copilot-gate.sh internals or a Python companion
- scripts/orchestrate-validate.py
- future pack validation
- release fitness checks

This gives all framework checks a common machine-readable report format.

### P1: Integrate cc memory check into setup/update/memory workflows

Add `cc memory check --json` guidance to:
- AGENTS.md and templates/AGENTS.project.template.md
- plugins/codex-copilot/skills/memory/SKILL.md
- docs/usage.md and docs/getting-started.md
- setup/update verification docs

Use cases:
- after setup-project
- after framework update
- after moving files, renaming docs, or updating project structure
- before major design-led decisions that depend on memory

This matters because stale memory can quietly corrupt product taste, architectural decisions, and user-journey assumptions.

### P2: Treat cc usage as optional, not core

Claude's `cc usage` is valuable in Claude because it surfaces Claude session quota and can feed a session-start hook. Codex Copilot should not promote it as a core design-led capability because:
- it reports Claude quota, not Codex/OpenAI usage
- Codex has no equivalent session-start hook here
- overemphasis could confuse users about what quota is being measured

Recommended adoption:
- mention it in docs/capabilities.md as an available cc utility
- optionally let the memory/config skill display it when the user asks about Claude Copilot tooling
- do not put it in the primary protocol checklist

### P2: Add pack manifest validation and fix writing-legal pack metadata

Add pack-level validation to smoke/release fitness:
- every packs/<name>/ with skills should have pack.json
- activate-pack.py should fail clearly and tests should cover included packs
- docs/packs.md should only list activatable packs or mark incomplete packs explicitly

This supports design-led software by making domain capability packs reliable without bloating the global specialist roster.

### P2: Strengthen design-led QA evidence

Add explicit QA acceptance language for product-facing changes:
- SOUL fit checked when SOUL.md exists
- UX states checked against uxd spec
- visual hierarchy checked against uids spec
- responsive/a11y checks recorded with artifacts
- screenshots or Playwright traces used when UI changed

This is the design-led version of Claude's artifact gate.

## What Not To Adopt

- Do not import Claude lifecycle hooks directly.
- Do not make `cco`, `cw`, `cs`, `cpa`, or `kc` globally active by default.
- Do not add automatic headless delegation beyond explicit user-approved spawn_agent use.
- Do not adopt auto-commit-on-completion without a separate Codex-specific design discussion.
- Do not make `cc usage` a primary Codex statusline or protocol gate.

## Suggested Implementation Sequence

1. Baseline/version refresh to Claude 5.10.0 / cc 1.4.0.
2. Artifact-bound QA gate and tests.
3. Schema-backed agent/catalog manifest with designChain and routingEdges.
4. Shared validation result module and script conversions.
5. Memory drift check integration in docs/templates/skills.
6. Pack manifest validation and writing-legal pack cleanup.
7. Design-fidelity artifact guidance for product-facing QA.

## Service/UX/UI/Architecture Lens

Service design: The framework should make handoffs explicit and recoverable. Artifact-bound QA and memory drift checks improve recovery because users can see what evidence supports a decision.

UX design: Users need lower cognitive overhead when deciding whether Codex has actually finished. A uniform ARTIFACT + VERDICT contract is clearer than prose-only QA summaries.

UI design/product language: Codex should preserve product taste by making SOUL/spec comparison a first-class QA artifact for product-facing work.

Architecture: Prefer schema-backed manifests and tc-visible checks over hidden hooks. This matches Codex-native boundaries and keeps the framework inspectable.
